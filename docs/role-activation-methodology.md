# Role Activation Methodology

## 原则

工作流 frontmatter 中的成员是候选池，不是默认全量参与名单。每个任务在执行前都必须建立 `rolePlan`，避免形式化协作、重复阅读和无证据评分。

```json
{
  "role": "member-id",
  "mode": "active",
  "reason": "触发该角色参与的场景依据。",
  "stages": ["阶段名称"]
}
```

`mode` 只能是：

- `active`：负责决策、产出、实现、验证或门禁。
- `consulted`：仅在明确范围内提供评审、咨询或证据补充。
- `not_applicable`：当前范围明确不适用；`stages` 必须为空，且不得生成虚假产物。

## 角色场景矩阵

| 角色 | ID | active 信号 | consulted 信号 | not_applicable 信号 |
| --- | --- | --- | --- | --- |
| 性能分析负责人 | `performance-lead` | 任何 standard/assurance 性能分析、跨角色诊断、方案评审或最终交付。 | lightweight 单点问题已有明确范围，只需确认结论边界和交付格式。 | 不适用；任何正式性能分析必须保留协调与交付责任，可由主分析者兼任。 |
| 前端源码性能分析师 | `source-performance-analyst` | 项目源码或构建产物可用，且任务要求根因定位、影响范围或实施交接。 | 仅有浏览器现象，需要判断最可能的代码区域或补充采样点。 | 没有任何源码、产物、source map 或实现上下文，且任务只评估外部页面表现。 |
| 浏览器性能测量工程师 | `browser-performance-engineer` | URL 或应用可运行，任务要求真实性能现状、运行时归因或 V3 结论。 | 页面暂不可访问，但需要设计测量协议或评审用户提供的 trace。 | 任务明确只做代码预审，且用户接受结论停留在 V1。 |
| 渲染与交互性能专家 | `rendering-performance-specialist` | 证据显示主线程、渲染流水线、交互响应、Hydration 或组件更新是主要瓶颈。 | 方案可能影响渲染或交互，但当前根因主要在加载、网络或服务端。 | 问题完全发生在资源传输、服务端响应或非交互静态内容，且无渲染副作用。 |
| 加载与网络性能专家 | `loading-performance-specialist` | 证据显示加载、网络、资源、构建、缓存或第三方是主要瓶颈。 | 主问题在渲染或交互，但方案会改变资源交付或构建产物。 | 任务只关注长会话交互或内存，且加载路径与资源策略无关。 |
| 现场性能数据分析师 | `field-performance-analyst` | 存在可信现场数据，或任务要求评估真实用户覆盖面与上线收益。 | 当前只有实验室数据，但需要设计后续 RUM 验证和预算。 | 无现场数据访问权，且任务明确只做实验室诊断。 |
| 性能优化方案架构师 | `performance-solution-architect` | 任务需要优化方案、影响范围、优先级、路线图或实施交接。 | 诊断阶段需要提前判断证据是否足以支持方案决策。 | 任务仅要求采集基线或复现现象，不要求方案。 |
| 性能证据与质量复核专家 | `performance-evidence-reviewer` | assurance 任务、完整评估、性能回退、P0/P1 结论或正式交付。 | standard 任务只需定向复核测量、归因或方案中的高风险部分。 | lightweight intake 或只输出测量计划，尚未形成性能结论。 |

## 重评条件

- 目标用户旅程、URL、代码版本、构建方式或性能目标发生变化。
- 静态分析与浏览器证据冲突，或重复测量方差超过预设容忍范围。
- 发现跨端、SSR/CSR 边界、服务端 TTFB、CDN、第三方脚本、内存泄漏或长会话问题。
- 浏览器访问受阻、现场数据缺失、认证或隐私边界变化。
- 方案影响公共基础设施、共享组件、缓存策略、监控口径或发布机制。
- 出现 P0/P1 风险、验证失败或用户要求进入实现阶段。

触发后必须重新评估 `rolePlan`，并同步更新状态、交接、评分和验证范围。

## 评分与交付

- 未激活领域不得给无证据评分；相关维度应标为 `N/A` 并说明依据。
- 交付摘要必须记录所有角色的实际贡献或未参与原因。
- `active` 角色必须有可追溯的产出、证据或门禁结论。
